## 面试先讲五分钟的证据链

1. **30 秒说明对象**：采用固定提交的 PULP APB UART；自己新增 SV/UVM 环境、模型、测试、回归和证据工具，并维护独立修复版；保留来源和许可。
2. **1 分钟讲架构**：APB monitor 给 TX 预测，UART monitor 从引脚独立解码实际帧；RX 也通过引脚观测与 RBR 读值比较。RAL 则用 sequencer 锁保持 DLAB 选择、目标访问和恢复的顺序，再按实际完成的 APB 事务预测 mirror；选择一段 RAL 日志讲清 bank 与硬件状态的关系。
3. **1 分钟讲边界**：TX 的 16 个 FIFO 槽位之外还有发送器；满时同周期出队仍拒绝新写。RX 第 17 帧暂存在接收器，模型不能直接按 16 字节截断。
4. **1 分钟讲缺陷**：选逐帧校验标记或中断确认，展示原版严格测试 FAIL、修复版 PASS。说明为什么只把常量清零接线改掉仍不足以修复“数据先入队、校验后产生”的关联问题。再选一个受控故障与正常对照，展示 checker 能检出相应错误。
5. **1 分钟讲覆盖与复现**：打开原始报告与一个 VCD，解释 seed、源码 SHA、完成标记、UVM ERROR/FATAL、功能 bin 与代码覆盖统计；按下面的三个分组说明数字，并打开已 [实际成功的 CI](https://github.com/jiangzheyi1234-star/apb-uart-uvm/actions/runs/45206296552) 展示远端运行产物。

面试时使用统一口径：**48/48 功能回归 = 核心 45 次 + RAL 3 次**，对应 16 类场景和 2,261 帧比对（核心 2,255 + RAL 6）。检查器对照另外执行 **10 次 = 4 次故障原始 FAIL + 6 次正常 PASS**；4/4 指指定故障均被 checker 检出，全部 10 次均不计入功能回归的 48 次或 2,261 帧。功能 bin 272/277（98.19%）和 RTL 行 453/474（95.57%）属于核心 45 次的覆盖结果。

默认 CI 验证核心 45 次、RAL 3 次和检查器对照 10 次；上游 45 次及严格 90 矩阵审计属于完整手动入口。两者已有独立成功记录：[默认 CI](https://github.com/jiangzheyi1234-star/apb-uart-uvm/actions/runs/45206296552)、[完整 CI](https://github.com/jiangzheyi1234-star/apb-uart-uvm/actions/runs/45209690986)，演示时按各自范围说明。入口见 [README](../README.md)，本地依据见 [发布回归](release/index.html)、[专项证据](features/index.html) 和 [验收](validation.md)。

## 十四个应能结合代码回答的问题

| 问题 | 回答抓手 / 演示位置 |
| --- | --- |
| APB 何时算一次完成事务？为什么在下降沿驱动？ | `PSEL && PENABLE && PREADY`；建立/访问两阶段；把驱动与 DUT 上升沿采样分开，说明 NBA 更新前的读值与副作用时序。看 `tb/apb_agent/` 和顶层 SVA。 |
| APB driver 支持等待，为什么没有 UART wait-state 覆盖？ | 本 DUT PREADY 恒 1。可复用 agent 的能力与这次 DUT 实际激励应分别证明。 |
| 为什么 32 位 APB 数据口的寄存器地址仍是 0～7？ | 实际译码只看 `PADDR[2:0]`，高位镜像；不能从总线宽度推导四字节寄存器间距。 |
| DLAB 为什么会影响 RAL？ | 地址 0/1 的用途随 LCR[7] 改变。讲 bank-aware frontdoor、多个访问的互斥和观察总线后的预测；FIFO/有副作用口不按普通存储寄存器自动 mirror。看 `tb/ral/README.md`。 |
| `set/get`、`write/read`、`predict/mirror` 有何区别？ | 区分 desired、mirrored 与硬件值；哪种操作实际发总线事务；为什么 predictor 应观察完成访问。用 RAL 实际测试示例说明，不背 API 名称。 |
| TX 写 21 次为何只有 17 帧？ | 慢波特率下首字节进发送器，16 字节进 FIFO，后 4 次写被忽略；展示周期级容量模型和严格计数。 |
| RX 第 17 帧如何保存？再来一帧会怎样？ | `SAVE_DATA` 被 ready 阻塞；只有一个额外保留槽，持续超载仍在范围边界中。不要宣称有完整 overrun 上报。 |
| Scoreboard 如何避免与 RTL 一起错？ | 激励、APB 观测、串行解码分别实现；不读 DUT 内部 FIFO。模型依据明确接口契约，并限制热切换/活跃清 FIFO 等未建模情况。 |
| reset 发生在 `fork` 内怎么办？ | driver/monitor 中止当前帧，复位清预测队列与计时；epoch 防旧帧在复位后进入比较。解释为什么 counters 可累计而预测状态必须清空。 |
| parity 与 framing flag 为什么要随字节入 FIFO？ | 原版先发 valid 再检查 parity，还固定清零错误；修复版在 parity/stop 检查之后提交 `{FE,PE,data}`，队首状态才与 RBR 对应。 |
| RX、线路错误和 TX 空中断如何确认？ | 区分电平条件与一次通知；优先级 line > RX > TX；IIR/LSR/RBR 的确认动作不同。IIR 低位无 pending 编码必须恢复。见 `rtl_fixed/uart_interrupt.sv`。 |
| 高覆盖率能证明什么？为什么保留未命中项？ | 先给覆盖模型和统计分母；解释帧格式、分频交叉与诊断 bin。功能 bin、代码行和代码分支分别统计；两态仿真不等于四态/X 签核。 |
| 没有实际检查也能 PASS 吗？ | 展示最少 TX/RX 检查次数、未消费队列检查、超时/进程退出/完整 UVM 汇总门禁；4 次受控故障均触发指定 checker，6 次正常对照均通过。解释为什么故障原始 FAIL 保留，且这 10 次不进入功能回归通过率。 |
| 如何把已有软件测试经验迁移过来？ | 用真实经历说明用例设计、边界复现、日志分析、缺陷闭环和回归；再用当前 RTL/UVM 项目补出硬件时序、SV 语言及模型能力，不把两者写成同一种行业经历。 |

## 接下来补基础和验证深度

按顺序准备数电与 SV 现场题：组合/时序逻辑、阻塞/非阻塞赋值、锁存器、复位、同步器、FIFO 指针及满空；再练 class 继承、virtual、随机约束、queue、mailbox、event、`fork/join` 和采样竞争。接着用本项目讲清 UVM phase、objection、factory override、config_db 路径、TLM analysis 与 RAL 的责任分界。

C/C++、Linux/Makefile 和脚本在已核验岗位中都有实际依据，可以用现有编程经验继续补强。商业仿真器练习、SoC 总线/中断、CDC/STA 基础及后仿应作为后续学习项；尚未运行的工具与未做过的流程不写成经验。

跨专业候选人应保留真实学位与专业。自动化本科可以用真实课程、工程和项目证明基础；若岗位按硕士专业设门槛，需要核对该职位的认定口径。项目材料应帮助对方评估技术能力，而非暗示学历已经满足所有筛选条件。GitHub 只发布工程与技术证据，个人联系方式、证件和整份简历继续留在私有目录。
